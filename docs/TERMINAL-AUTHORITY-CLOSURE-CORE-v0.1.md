## 2. One acyclic selected contract, not one global epoch

Let D be SHA256 of the complete raw bytes of this core. The schema companion pins that 32-byte value and the exact body keys. This core must not contain its own digest or a hash of a document containing that digest. Detached adoption binds core, schema, plan and exact input inventory together. The semantic dispatch rule requires adoption as well as D equality; unadopted/unknown D is unavailable, never an accepted route.

Receipt selection, Request selection and terminal selection are separate local checks, even though this proposed package deliberately binds them to the same D. The Request and terminal markers do not select Freeze; the Receipt marker does not select Request or terminal. The Result has no new marker: its exact retained Request authority selects only the Request-derived validation of that Result. All identities are rederived from the same captured raw bytes used for decoding.

Selection table:
1. Receipt marker absent: predecessor Receipt/Freeze replay only; do not invoke this closure's identity/profile/positive replay rules. Exact marker: new Freeze route. Present malformed, duplicate, noncanonical, wrong or unknown value: fail closed, no predecessor fallback.
2. Request marker absent: predecessor Request handling, not new context-5 profile authorization. Exact marker: new Request route. Invalid present marker: fail closed with no fallback.
3. Terminal old key 24 absent and new marker absent: predecessor terminal handling.
4. Terminal old key 24 exact and new marker absent: the already adopted v0.10.9 route, including its exact singleton context-2 guard. Do not widen it from a Request marker or Policy contents.
5. Terminal old key 24 exact AND new marker exact: new terminal route; require the exact selected Request, its Result and selected Freeze chain under this same D.
6. Every other terminal marker combination fails closed without downgrade. In particular new marker without exact old marker is invalid. A new terminal cannot consume an unselected Request/Freeze as new authority.

The old terminal key-24 value remains exactly the raw SHA256 of the prior Authority-Path adoption record, not D. No producer backfills markers. No date, process state, source version, equal field values, configuration, current head, or nearby record implies selection. Old schemas remain supported only to their actual predecessor extent, not as a compatibility promise of positive authority.

### 3.1 Exact selected Subject-content derivation

This is an additional proposed semantic assignment, not a deduction from the baseline OpaqueId32 fields or the optional ArtifactSet Aggregate utility. For the selected regular-file lane, define A to be the complete Artifact Entry array in Schema v0.3 section 53's exact row form `[artifact_kind_id, path_components, size_bytes, digest_algorithm_id, digest_bytes]`, sorted by the already adopted canonical component-path comparator with no duplicate canonical paths. Every row has artifact_kind_id=1, digest_algorithm_id=1, exact consumed byte count and the raw 32-byte SHA256 digest of that file's retained bytes. CanonicalPath component types and bytes follow adopted path identity profile1. Let N be the actual array length, validated equal to Manifest.artifact_count. All integers obey the frozen restricted unsigned-integer domain.

The selected Subject value is the raw 32-byte SHA256 digest of the exact deterministic CBOR array:

`["EvidenceRegistry.Subject.RegularFiles.v1", 1, 1, N, A]`

The text is that exact UTF-8 domain string with no NUL suffix. The two UInt1 elements are respectively path_identity_profile_id and digest_profile_id. The final array is empty when N=0; that exact empty frame has one defined digest, not an absent Subject. This selected projection intentionally excludes subject_id itself, all Record framing/body metadata, RegistryId, AttemptId, Policy, labels, environment, physical roots/locators and the Manifest RecordId. Those exclusions prevent a self-hash cycle and preserve content identity independently of Record and Registry identity. This is not an alias for the optional ArtifactSet Aggregate utility, and it creates no separate independently supplied aggregate authority.

Before START, the Store reads/adopts the complete source regular-file inventory and exact bytes, computes each row digest/count and this selected Subject, and stores that value in START.subject_id. After retained-copy creation, it independently constructs A from retained bytes, recomputes the same projection, compares it to START, and uses it in Manifest.subject_id and Receipt.subject_id under existing cross-record equalities. Source re-comparison remains separate and mandatory. On selected event101 replay, obtain the exact referenced Manifest, strictly validate its profiles/A/N, recompute this Subject projection, require equality with Manifest, START and Receipt, and then verify every retained payload against the same A. A coherent substitution of all three opaque Subject fields without matching this recomputation rejects even if all Record/Journal hashes have been recomputed. No caller-provided Subject or aggregate replaces this derivation.

The unmarked START and MANIFEST grammars still carry OpaqueId32. Their generic prefix/staging interpretation is unchanged; the extra derivation relation is checked only by this selected producer and the selected Receipt consumer. Matching Subject bytes never select a route. Older unselected Freeze histories are not tested against this derivation or repaired by it. Full Record identities continue to hash their complete bytes, including their resulting Subject field.

## 4. Required profile references and retained payload mapping

New type 64 FREEZE_CREATION_PROFILE, schema version 1, profile_id 1 denotes precisely the bounded procedure in this section. Its closed grammar is in the schema companion. Its RecordId uses unchanged complete Record framing; no Journal event is required for this static parameter Record. A selected Receipt.creation_profile_ref must resolve from records/ to that exact typed profile, not an arbitrary frame-valid object.

For this selected lane, Receipt.filesystem_profile_ref explicitly names the exact type-61 ENVIRONMENT_OBSERVATION Record named by the committing event 101's environment_observation_id. This deliberate reuse is a new typed-reference rule, not an inference from the old field name. That observation describes the actual Store operation's filesystem context. Its absence, type mismatch, identity mismatch, or disagreement with the event rejects before completion. The associated type-60 capability class must resolve from the event's exact identity and be coherent with the current capability epoch. Unknown observation fields remain unknown and cannot establish an unobserved capability. Neither profile Record certifies that syscalls happened merely by existing.

The canonical retained payload base is exactly R/roots/<attempt-hex>/payload/. Each canonical Manifest path component maps directly, without normalization or escaping, to one descendant component under that base. The final component names a regular file; preceding components name real directories. An adapter unable to represent the exact recorded UTF-8/path grammar faithfully rejects the selected operation as unsupported. In particular it must not repair reserved names, case collisions, normalization differences, aliases or alternate streams. Metadata and Records remain outside payload/; the only direct child of a completed selected root is payload/.

Creation owns this sequence:
1. Authoritatively record and read back START while holding the attempt coordination lock. Its Subject binding must be derived from admitted source bytes/inventory, not a caller's asserted identity.
2. Exclusively create the exact derived root and payload directory; no reused root, truncate, existence-check substitute, silent Attempt regeneration or symlink/reparse traversal.
3. Read each admitted source regular file, create a retained copy through exclusive staging and atomic no-replace publication at its exact payload path, hash the retained copy, construct the Manifest from those retained bytes, and verify the retained copy against it.
4. Separately re-enumerate/compare the source with the copy-derived Manifest, with complete admitted artifact coverage. Compare source-derived intended Subject with the final copy-derived Subject and START binding. Any disappearance, unreadable object, changed admitted bytes/inventory, extra or missing artifact, ambiguous identity, hardlink alias, special file, stream, reparse point or unsupported path fails closed; nothing is silently skipped. Reject links conservatively; this profile does not activate an optional link policy.
5. Flush the retained payload files and every directory entry created or published for this payload/root before constructing the Receipt. Retain operation-owned evidence of which actions actually completed. Source Binding Record remains required whenever the operation is intended for later source matching, under its existing grammar and semantics; locator hints are not authority.
6. Revalidate the same retained root and payload generation, all exact Manifest bytes/digests/counts, typed profiles, START and Policy before the final decision.

The Receipt's three action-state fields are scoped only to this completed payload/root preparation: file-content flush covers every retained payload file; atomic no-replace covers publication of every payload file's final name; parent-directory flush covers every containing directory entry changed by this root/payload construction. An empty file set does not invent a syscall: file-content and file-publication states are NOT_PERFORMED when no corresponding file action exists; root/payload directory creation still requires its actual directory flush. PERFORMED means every required action in that nonempty category actually completed; unsupported or failed required actions block positive production. platform_strongest_available is false in this bounded profile: it makes no strongest-available claim. These fields exclude later publication of the Receipt itself and the Journal slot.

Reopen resolves payloads only through this selected mapping and checks exact complete file inventory, canonical paths, byte lengths/digests and retained root generation; extra files and unexpected non-payload children reject. Empty traversal directories neither change SubjectId nor prove extra artifacts. Historical physical actions remain local-producer assertions retained in the Receipt, not independently re-observed past syscalls. Current missing/corrupt embedded bytes prevents current positive selected Freeze authority; no physical deletion or repair is performed by inspection.

## 6. Store production, serialization and durability

The adopted Store v0.1 namespace, strict GENESIS duplicate and slot-zero bindings, retained root-to-START relation, exact resolution, generation revalidation and cooperative Profile L remain mandatory. A new explicitly selected Store API must implement that profile; it must not claim that the older three-namespace opener already does. Read-only opening never initializes, synthesizes missing GENESIS Records, normalizes names, appends recovery or repairs material.

For this selected Store profile, explicitly assign GENESIS.journal_format_version=1 to the exact Journal Entry/JournalReference encodings and hash algorithms of frozen Identity Format v0.3, and GENESIS.record_identity_profile_id=1 to that document's sections33-36 complete deterministic-CBOR Record framing and SHA256 RecordId derivation. These are new proposed value-to-contract mappings, not inferred aliases of a Record's outer schema_version. Initialization must emit those exact UInt values; selected Store open must validate both values and the actual encoding/identity contract before positive selected operations. A wrong/unknown scalar yields UNSUPPORTED_CAPABILITY in the selected profile; malformed framing/duplicates remain INVALID_PREREQUISITE. Generic predecessor UInt decoding is unchanged. A value1 in an older GENESIS is not a D selector, does not prove historical producer behavior and cannot upgrade any unselected downstream record; it can satisfy only the explicitly checked format prerequisite for a newly selected operation. Every prefix-derived JournalAnchor obtains its journal_format_version from this exact validated retained GENESIS, and it must equal1; neither caller input nor the Anchor's distinct outer schema_version supplies it.

This supplement names operational locations needed by actual adapters: coordination/publication.lock is the cooperative root-writer lock; coordination/staging/<32-lowercase-hex-random-token>.tmp is an exclusive regular temporary file. These and the already assigned coordination/freeze/<attempt-hex>.lock are nonauthoritative; they never select replay or prove liveness. staging/ is a real directory. Only these exact operational grammars are allowed; arbitrary .tmp files in records/, journal/ or Store root are not ignored. Unknown operational files, aliases and type violations fail closed. Recognized interrupted staging files grant no authority and may remain without blocking read-only replay; cleanup is a separately locked maintenance action, never an inspection side effect. No auto-resume follows from a lockfile or temp file. All no-replace final publication stays on the same qualified filesystem; unsupported cross-filesystem operations reject.

The selected nonauthoritative capability-probe namespace is coordination/staging/, using only its exclusive regular-file temporary grammar above; the existing coordination directories may be observed and flushed without inventing probe artifacts in authoritative namespaces. Probes must not create temporary files in journal/, records/ or roots/. Lifecycle section 110.1's exemption for creation of type60/type61 observations remains in force: producing an observation does not recursively require another observation. A required probe that cannot be expressed safely in the selected namespace is unsupported, not permission to add a new namespace or pretend it ran.

Store initialization is a separate explicitly authorized operation, on an absent root only. It first exclusively creates and retains the exact root and required namespace directories, including the operational staging/ and coordination directories, under one live initialization ownership witness. It then obtains real operation-scoped capability/environment observations at that exact root, stages all required typed GENESIS/observation Records and the exact registry/genesis.cbor duplicate, constructs/preflights the initial entry, publishes slot zero, flushes and performs exact selected reopen. Initialization is the sole exception to the following generic pre-append requirement to reopen an already authoritative Store: before slot zero exists, preflight validates the owned candidate GENESIS/observation bytes and initial transition, rather than synthesizing a retained GENESIS or calling ordinary open on a partial Store. After slot zero, ordinary strict reopen/readback is mandatory. A partial initialization is non-success and never auto-completed by open. This is not permission to initialize an existing root as a repair or to resume a lost live initialization witness.

For every authoritative append, acquire root serialization, re-open/replay the current exact retained state, observe or validly reuse the operation-relevant capability context, and derive the exact next slot from it. GENESIS observations are not eternal current capability evidence. Bounded cache reuse requires every existing process/context/epoch condition; this implementation may simply probe freshly instead. If a material capability change needs event 600 but its numeric transition mapping is unsupported, stop before the requested operation rather than inventing that mapping or silently reusing the prior class.

For terminal Admission, perform all history-sensitive §82/§46 checks and construction while holding the same root serialization through append. L(A) remains the captured acceptance-start reference, never the later publication head. Revalidate it at publication, but never refresh it. A conflict, replaced generation or changed relevant observation ends this attempt without reusing its completed result; no stale-Anchor/evaluator result is retried against a new head. New acceptance is a new operation after the old one is explicitly non-success. Loss of the live operation witness creates no replayable continuation token.

No success follows from same bytes alone, unsupported flush or best-effort fallback. ## 7. Positive replay and inspection meaning

A captured Store view must be identified as a view of its exact head, not a fresh observation of a later filesystem state. The existing Journal-only CLI remains Journal-only unless separately authorized and qualified to expose Store semantics.
